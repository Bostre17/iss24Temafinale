LABORATORIO DI INGEGNERIA DEI SISTEMI SOFTWARE

Introduzione

Lo Sprint 3 rappresenta il completamento del sistema WasteIncineratorService attraverso l'implementazione dello strato di presentazione. In questo sprint si sviluppa la ServiceStatusGUI, un'interfaccia web-based accessibile tramite browser per visualizzare lo stato del sistema.

Negli sprint precedenti sono stati implementati:

  • Sprint 1: Core business logic (WIS, OpRobot, Incinerator)
  • Sprint 2: Integrazione dispositivi fisici (Sonar, Scale, LED su RaspberryPi)

Questo sprint fornisce agli operatori uno strumento per monitorare:

  • Stato corrente dell'incineritore (Off/On/Idle)
  • Livello di riempimento del WasteStorage (numero di RP presenti)
  • Stato dell'AshStorage (pieno/non pieno)
  • Posizione e attività corrente dell'OpRobot

Sprint 3 - ServiceStatusGUI

Goal dello Sprint

Obiettivo principale: Implementare un'interfaccia grafica web-based (ServiceStatusGUI) che visualizzi lo stato di tutti i componenti del WasteIncineratorService.

Requisiti funzionali:

  • Visualizzazione dello stato dell'Incinerator (Off/On/Idle)
  • Visualizzazione del numero di RP presenti nel WasteStorage
  • Visualizzazione dello stato dell'AshStorage (pieno/non pieno)
  • Visualizzazione della posizione corrente dell'OpRobot
  • Visualizzazione dell'attività corrente dell'OpRobot
  • Aggiornamento automatico della GUI

Requisiti non funzionali:

  • Coerenza con sprint precedenti: utilizzo di Gradle come build tool
  • Accessibilità: interfaccia utilizzabile da qualsiasi browser moderno
  • Semplicità architetturale: separazione chiara tra business logic e presentation

Requisiti

Come specificato nello Sprint0, la ServiceStatusGUI deve fornire le seguenti informazioni:

  • Stato Incinerator: Visualizzazione se spento (Off), acceso (On), o in attesa (Idle)
  • Stato WasteStorage: Numero di RP presenti, calcolato dal peso misurato dalla Scale
  • Stato AshStorage: Indicazione se il deposito ceneri è pieno o meno
  • Stato OpRobot: Posizione corrente e attività in corso

Analisi del Problema

P1 - Scelta del Build Tool

Gli Sprint 1 e 2 utilizzano Gradle come build tool. Per mantenere coerenza nel progetto, si decide di utilizzare un unico build.gradle che gestisca sia:

  • Il sistema QAK (business logic)
  • L'applicazione Spring Boot (presentation layer)

Vantaggi di questa scelta:

  • Coerenza: stesso tool utilizzato in tutto il progetto
  • Semplicità: un solo file di configurazione build
  • Flessibilità: task separati per avviare QAK e GUI

P2 - Architettura della GUI

Si valutano diverse opzioni per implementare l'interfaccia web:

Opzione A: HTML Statico con JavaScript Polling
  • Pro: Massima semplicità, nessuna dipendenza
  • Contro: Richiede web server esterno (Python, Node, Nginx)
Opzione B: Spring Boot con Thymeleaf - SCELTA
  • Pro: Web server integrato, template engine professionale
  • Pro: Auto-refresh semplice tramite meta tag HTML
  • Pro: Integrabile in un unico build.gradle
  • Contro: Richiede dipendenze Spring Boot (gestite automaticamente da Gradle)

Decisione: Optiamo per Spring Boot + Thymeleaf perché:

  • Soluzione completa e auto-contenuta
  • Web server embedded (Tomcat)
  • Template engine per rendering server-side
  • Gestibile con Gradle tramite plugin Spring Boot

P3 - Fonte delle Informazioni

Il WIS mantiene già lo stato completo del sistema, essendo Observer di tutti i componenti. Per rendere accessibili queste informazioni alla GUI, si introduce un componente GUIBridge (attore QAK) che:

  • Si subscribe agli eventi rilevanti del sistema
  • Mantiene una cache dello stato corrente
  • Espone i dati tramite updateResource di QAK
  • Rende disponibile lo stato via HTTP su http://localhost:8001/api/guibridge

P4 - Gestione Eventi da Context Esterni

Un problema tecnico emerso durante l'implementazione riguarda la ricezione di eventi da attori in context esterni.

Problema: Subscribe a MonitoringDevice

Il MonitoringDevice risiede in un context esterno (ctxmd). Non è possibile fare:

subscribeTo monitoringdevice for stateSonar  // ERRORE!

perché subscribeTo funziona solo con attori nello stesso context.

Soluzione: Eventi Globali

In QAK esistono due tipi di eventi:

  • Eventi Locali: emitlocalstream evento : evento(dati) - solo nel context corrente
  • Eventi Globali: emit evento : evento(dati) - broadcast a tutti i context

Il MonitoringDevice utilizza emit stateSonar (evento globale), quindi GUIBridge può riceverlo automaticamente senza subscribeTo:

State s0 initial {
    // Subscribe solo agli attori LOCALI (stesso context)
    subscribeTo incinerator for burnEnd
    subscribeTo scale for stateScale
    
    // Per stateSonar: NON serve subscribeTo
    // Viene ricevuto automaticamente nella transition
}
Transition t0 whenEvent stateSonar -> updateAshStorage

P5 - Meccanismo di Aggiornamento GUI

La GUI utilizza un meccanismo di auto-refresh HTTP:

  • Meta tag HTML: <meta http-equiv="refresh" content="2">
  • Ogni 2 secondi il browser ricarica completamente la pagina
  • Il server (Spring Boot) interroga GUIBridge ad ogni richiesta
  • Il template Thymeleaf viene re-renderizzato con i nuovi dati

Vantaggi:

  • Implementazione semplicissima (1 riga HTML)
  • Nessun JavaScript complesso
  • Funziona su qualsiasi browser
  • Affidabile e predicibile

Componente 2: GUIBridge (QAK Actor)

GUIBridge mantiene lo stato del sistema e lo espone via HTTP:

QActor guibridge context ctxwis {
    [#
        var incineratorState = 2  // 0=Off, 1=On, 2=Idle
        var rpCount = 0
        var ashStorageFull = 0
        var robotX = 0
        var robotY = 0
        var robotJob = "Waiting Home"
        
        fun buildStateString(): String {
            return "incinerator=$incineratorState," +
                   "rp=$rpCount,ash=$ashStorageFull," +
                   "x=$robotX,y=$robotY,job=$robotJob"
        }
    #]
    
    State s0 initial {
        println("[$name] GUI Bridge ready") color cyan
        
        // Subscribe attori LOCALI
        subscribeTo incinerator for burnEnd
        subscribeTo scale for stateScale
        
        // stateSonar è evento GLOBALE - ricevuto automaticamente
        
        updateResource [# buildStateString() #]
    }
    Goto ready
    
    State ready { }
    Transition t0 
        whenEvent stateScale -> updateRpCount
        whenEvent stateSonar -> updateAshStorage
        whenEvent burnEnd -> updateIncinerator
    
    State updateRpCount {
        onMsg(stateScale : stateScale(X)) {
            [# rpCount = payloadArg(0).toInt() / 50 #]
            updateResource [# buildStateString() #]
        }
    }
    Goto ready
    
    // ... altri stati simili
}

Componente 3: WISFacade (Spring Boot)

Applicazione Spring Boot che serve come ponte tra QAK e browser:

@SpringBootApplication
@Controller
public class WISFacadeApp {
    
    @GetMapping("/")
    public String dashboard(Model model) {
        SystemState state = fetchStateFromGUIBridge();
        
        model.addAttribute("incineratorState", state.incinerator);
        model.addAttribute("incineratorText", 
            getIncineratorText(state.incinerator));
        model.addAttribute("rpCount", state.rpCount);
        model.addAttribute("ashFull", state.ashFull);
        model.addAttribute("robotX", state.robotX);
        model.addAttribute("robotY", state.robotY);
        model.addAttribute("robotJob", state.robotJob);
        model.addAttribute("timestamp", new Date());
        
        return "dashboard";
    }
    
    private SystemState fetchStateFromGUIBridge() {
        RestTemplate restTemplate = new RestTemplate();
        String response = restTemplate.getForObject(
            "http://localhost:8001/api/guibridge", String.class);
        return parseState(response);
    }
    
    private SystemState parseState(String stateString) {
        // Parse: "incinerator=2,rp=0,ash=0,x=0,y=0,job=..."
        Map<String, String> data = new HashMap<>();
        for (String pair : stateString.split(",")) {
            String[] keyValue = pair.split("=", 2);
            data.put(keyValue[0], keyValue[1]);
        }
        // Popola SystemState...
    }
}

Troubleshooting

Problema: GUI mostra sempre valori 0

Causa: GUIBridge non raggiungibile o non in esecuzione

Soluzione:

  1. Verificare che gradlew runQAK sia in esecuzione
  2. Testare endpoint: curl http://localhost:8001/api/guibridge
  3. Verificare log per errori di connessione
Problema: Errore "Port 8080 already in use"

Causa: Porta 8080 occupata da altro processo

Soluzione:

Modificare application.properties:

server.port=8081

Poi accedere a http://localhost:8081

Problema: Compilazione fallisce

Causa: Java version < 17

Soluzione:

Verificare versione Java:

java -version  # Deve essere >= 17

Installare Java 17 se necessario

Conclusioni

Lo Sprint 3 completa il WasteIncineratorService con un'interfaccia web professionale mantenendo la coerenza architetturale con gli sprint precedenti.

Punti di forza della soluzione:

  • Gradle Unificato: Un solo build.gradle gestisce QAK e Spring Boot
  • Coerenza: Stesso build tool utilizzato in Sprint 1 e 2
  • Semplicità: Auto-refresh tramite meta tag HTML (nessun WebSocket/AJAX complesso)
  • Separazione: Business logic (QAK) e Presentation (Spring Boot) ben separati
  • Flessibilità: Due task separati (runQAK e runGUI)
  • Manutenibilità: Template Thymeleaf modificabili senza ricompilare Java

Aspetti tecnici risolti:

  • Gestione eventi da context esterni tramite eventi globali
  • Integrazione Spring Boot in progetto Gradle QAK esistente
  • Esposizione stato QAK tramite HTTP (updateResource)
  • Rendering server-side con Thymeleaf

Il sistema risultante fornisce agli operatori uno strumento efficace per monitorare il WasteIncineratorService in tempo reale, accessibile da qualsiasi browser senza necessità di installazione software aggiuntivo.
