LABORATORIO DI INGEGNERIA DEI SISTEMI SOFTWARE

Introduzione

Un'azienda intende sviluppare un WasteIncineratorService per il trattamento dei rifiuti tramite incenerimento e necessita di un servizio di sistema software (WIS) per controllare un robot (chiamato OpRobot) per lo spostamento dei rifiuti.

Questo documento contiene lo Sprint 3 del progetto, che si concentra sul livello di presentazione e sul monitoraggio remoto, estendendo il lavoro svolto nello Sprint 2.

L'obiettivo principale è lo sviluppo della ServiceStatusGUI, un'interfaccia web che permette agli operatori di visualizzare lo stato del sistema in tempo reale, e la conseguente integrazione con il Sonar fisico montato sul Raspberry. In questa fase viene introdotta un'architettura Event-Driven basata su protocollo MQTT, finalizzata a disaccoppiare la logica di controllo dalla visualizzazione e a garantire aggiornamenti reattivi dello stato dei componenti (Incinerator, Scale, MonitoringDevice e Robot).

Sprint 3 - ServiceStatusGUI

Goal dello Sprint

Obiettivo principale: Implementare un'interfaccia grafica web-based (ServiceStatusGUI) che visualizzi lo stato di tutti i componenti del WasteIncineratorService.

Requisiti funzionali:

  • Visualizzazione dello stato dell'Incinerator (Off/On/Idle)
  • Visualizzazione del numero di RP presenti nel WasteStorage
  • Visualizzazione dello stato dell'AshStorage (pieno/non pieno)
  • Visualizzazione della posizione corrente dell'OpRobot
  • Visualizzazione dell'attività corrente dell'OpRobot
  • Aggiornamento automatico della GUI

Requisiti non funzionali:

  • Coerenza con sprint precedenti: utilizzo di Gradle come build tool per il backend QAK
  • Accessibilità: interfaccia utilizzabile da qualsiasi browser moderno
  • Semplicità architetturale: separazione chiara tra business logic e presentation

Requisiti

Come specificato nello Sprint0, la ServiceStatusGUI deve fornire le seguenti informazioni:

  • Stato Incinerator: Visualizzazione se spento (Off), acceso (On), o in attesa (Idle)
  • Stato WasteStorage: Numero di RP presenti, calcolato dal peso misurato dalla Scale
  • Stato AshStorage: Indicazione se il deposito ceneri è pieno o meno
  • Stato OpRobot: Posizione corrente e attività in corso

Analisi del Problema

P1 - Scelta del Build Tool e Tecnologia Frontend

A differenza delle iterazioni precedenti, per questo Sprint si valuta la necessità di un backend dedicato per la GUI. L'analisi dei requisiti evidenzia che l'interfaccia deve essere reattiva e "real-time".

Si decide di non utilizzare Spring Boot per questo layer, optando per una soluzione 100% statica basata su tecnologie web standard (HTML5, CSS3, JavaScript ES6).

Vantaggi di questa scelta:

  • Disaccoppiamento totale: La GUI è indipendente dal ciclo di vita del server Java.
  • Deployment semplificato: I file statici possono essere ospitati ovunque (GitHub Pages, AWS S3, web server locale) senza configurare application server.
  • Leggerezza: Eliminazione dell'overhead di un container servlet (Tomcat) per la sola visualizzazione dati.

P2 - Architettura della Comunicazione (Polling vs Event-Driven)

Si valutano le opzioni per l'aggiornamento dei dati:

Opzione A: HTTP Polling (Approccio precedente)
  • Meccanismo: Il browser richiede i dati ogni X secondi (es. meta-refresh).
  • Contro: Latenza, carico inutile sul server se lo stato non cambia, esperienza utente "a scatti".
Opzione B: MQTT over WebSockets - SCELTA
  • Meccanismo: Il browser stabilisce una connessione persistente WebSocket con un Broker MQTT.
  • Protocollo: MQTT (Message Queuing Telemetry Transport) via WebSockets (wss://).
  • Pro: Aggiornamento Real-Time (push), pattern Pub/Sub nativo del sistema QAK, riduzione del traffico di rete.

P3 - Fonte delle Informazioni

Non è più necessario un componente "GUIBridge" che agisca da intermediario HTTP. La GUI diventa un client diretto del sistema di messaggistica:

  • Gli attori QAK (Incinerator, Scale, MonitoringDevice) pubblicano eventi sul topic MQTT sprint3.
  • La GUI (client JavaScript) effettua la subscribe allo stesso topic.
  • Il Broker MQTT (es. test.mosquitto.org) gestisce l'instradamento dei messaggi.

P4 - Formato dei Dati

Il sistema QAK emette messaggi nel formato Prolog-like standard: msg(eventType, event, emitter, receiver, eventType(payload), id).

La GUI deve essere in grado di effettuare il parsing di queste stringhe lato client. Si utilizzeranno espressioni regolari (Regex) in JavaScript per estrarre il payload significativo (es. il valore del peso o lo stato del sonar) direttamente dal messaggio grezzo.

Progettazione

Componente 1: Frontend Statico

La struttura del progetto frontend è composta da file statici puri, eliminando la necessità di compilazione Gradle per la parte GUI:

WasteIncineratorGUI/
├── index.html              # Dashboard principale
├── css/
│   └── dashboard.css       # Stili e animazioni LED
└── js/
    └── dashboard-mqtt.js   # Logica client MQTT

Componente 2: Integrazione MQTT.js

La logica di connessione risiede interamente nel browser tramite la libreria MQTT.js caricata via CDN. La configurazione prevede l'uso di WebSocket Secure (wss) per garantire la compatibilità con i moderni browser:

// Configurazione Broker
const mqttOptions = {
    clean: true,
    connectTimeout: 4000,
    clientId: 'wis_gui_' + Math.random().toString(16).substr(2, 8),
};
const brokerUrl = 'wss://test.mosquitto.org:8081'; // MQTT over WebSocket

// Connessione
const client = mqtt.connect(brokerUrl, mqttOptions);

client.on('connect', function () {
    console.log('Connected to MQTT Broker');
    client.subscribe('sprint3', function (err) { ... });
});

Componente 3: Parsing degli Eventi QAK

La GUI riceve i messaggi grezzi dal broker e li interpreta. Il parsing avviene tramite Regex per supportare il formato standard QAK msg(...):

client.on('message', function (topic, message) {
    const msgStr = message.toString();
    
    // Regex per estrarre: EventType, Emitter, Payload
    const qakMatch = msgStr.match(/msg\((\w+),\s*event,\s*(\w+),\s*\w+,\s*\w+\(([^)]*)\)/);
    
    if (qakMatch) {
        const eventType = qakMatch[1]; // es. stateScale
        const payload = qakMatch[3];   // es. 150
        
        updateInterface(eventType, payload);
    }
});

Componente 4: Aggiornamento UI Dinamico

L'aggiornamento del DOM avviene via jQuery/Vanilla JS in risposta agli eventi, garantendo un feedback visivo immediato:

  • stateScale(V): Aggiorna il contatore RP e la progress bar del WasteStorage.
  • stateSonar(V): Modifica lo stato (badge FULL/EMPTY) e attiva l'animazione LED.
  • burnEnd(V): Aggiorna lo stato dell'inceneritore da Burning a Idle.

Test Plan

T1 - Verifica Flusso MQTT

Obiettivo: Verificare che i messaggi QAK arrivino correttamente al broker.

Strumento: MQTT Explorer o mosquitto_sub.

mosquitto_sub -h test.mosquitto.org -p 1883 -t "sprint3" -v

Risultato atteso: Visualizzazione dei messaggi msg(stateScale, ...) quando il sistema è attivo.

T2 - Test GUI Standalone (Mocking)

Obiettivo: Verificare la GUI senza avviare il backend QAK.

Procedura: Utilizzare la console del browser per simulare l'arrivo di messaggi o usare uno script di pubblicazione manuale.

// Nella console del browser
handleMessage("sprint3", "msg(stateScale, event, scale, none, stateScale(200), 1)");

Risultato atteso: L'indicatore "Waste Storage" deve aggiornarsi istantaneamente a 4 RP (200kg).

T3 - Test End-to-End Real-Time

Obiettivo: Verificare la sincronizzazione tra Robot fisico/virtuale e GUI.

Procedura: Avviare il sistema QAK completo e aprire index.html.

Risultato atteso: Quando il robot deposita un RP (evento fisico), la GUI deve aggiornarsi entro pochi millisecondi grazie al push MQTT, mostrando l'animazione sulla mappa e l'aggiornamento dei contatori.

Conclusioni

Lo Sprint 3 completa il WasteIncineratorService con un'interfaccia web moderna e altamente reattiva, sfruttando un'architettura Event-Driven.

Punti di forza della soluzione:

  • Zero-Backend UI: Eliminata la complessità di Spring Boot per la parte di visualizzazione.
  • Real-Time nativo: L'uso di MQTT over WebSockets garantisce latenze minime rispetto al polling HTTP.
  • Scalabilità: Il broker MQTT disaccoppia i produttori di dati (Robot/Sensori) dai consumatori (Browser), permettendo a molteplici dashboard di connettersi simultaneamente senza impattare sul WIS.
  • Portabilità: L'intera GUI è costituita da file statici, facilmente distribuibili su qualsiasi hosting web.

Il passaggio a un'architettura basata su messaggi non solo semplifica il deployment, ma allinea il sistema agli standard IoT moderni, dove la comunicazione asincrona e il disaccoppiamento sono requisiti fondamentali.
