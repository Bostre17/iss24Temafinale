LABORATORIO DI INGEGNERIA DEI SISTEMI SOFTWARE

Introduzione

Un'azienda intende sviluppare un WasteIncineratorService per il trattamento dei rifiuti tramite incenerimento e necessita di un servizio di sistema software (WIS) per controllare un robot (chiamato OpRobot) per lo spostamento dei rifiuti.
Questo documento contiene lo Sprint2 del progetto, che si concentra sull'interazione con l'ambiente fisico: l'obiettivo principale è la corretta gestione e simulazione dei dispositivi esterni, in particolare Scale, Sonar e LED dove, gli ultimi due fanno parte del MonitoringDevice.

Sprint precedente

Il seguente link rimanda allo sprint precedente, ovvero lo Sprint1, in cui è stata sviluppata la prima architettura del core business, definendo il modello di interazione e la struttura dei componenti (WIS-OpRobot-Incinerator), permettendoci di modellare la logica operativa iniziale del sistema.

Sprint2

Analisi del Problema

    P2.1 - Modellazione del sistema relativo al MonitoringDevice

    Il sistema di monitoraggio (MonitoringDevice) deve interagire direttamente con l'hardware (Sonar, LED) installato fisicamente presso l'AshStorage. Ciò impone l'uso di un nodo computazionale locale (es. Raspberry Pi). Il WIS rappresenta la logica di business centrale e non ha vincoli di prossimità fisica con i sensori: per riflettere questa distribuzione fisica nel modello logico, è necessario ripartire gli attori su due nodi computazionali distinti.
    Nel metamodello QAK, ciò si traduce nella definizione di due contesti separati (ctx_monitoring e ctx_wis) che comunicheranno via rete. 
    Context ctx_monitoring  ip [host="x"] port ...
Context ctx_wis         ip [host="y"] port ...

    Il problema principale è: come rappresentare queste entità nel sistema software affinché siano gestibili dalla logica di business?
    • Sonar: Deve nascondere la complessità della lettura hardware (es. polling su script Python o lettura GPIO) e presentare un'interfaccia a messaggi.
    • WarningDevice: Rappresentazione logica del dispositivo fisico LED. Deve tradurre intenti logici (es. on, off e blink) in segnali fisici.
    QActor sonar context ctx_monitoring { ... }
QActor warningdevice context ctx_monitoring { ... }

    P2.2 - Modellazione di Scale

    La Scale è descritta nei requisiti come un dispositivo che pesa gli RP presenti nel WasteStorage. A livello di analisi, la Scale è una sorgente di dati attiva o passiva?
    Considerando che il peso cambia dinamicamente all'arrivo di nuovi RP, è opportuno modellarla come un attore attivo che monitora il peso e rende disponibile l'informazione. 
    QActor scale context ctx_wis { ... }

    P2.3 - Definizione Logica di AshStorage (Pieno/Vuoto)

    L'analisi dei requisiti stabilisce che lo stato dell'AshStorage dipende da una misura di distanza:
    • Pieno: Distanza sonar ≤ DLIMT.
    • Non Pieno: Distanza sonar > DLIMT.

    P2.4 - Comunicazione MonitoringDevice -> WIS

    Il MonitoringDevice possiede l'informazione sullo stato della cenere. Il WIS necessita di questa informazione per bloccare/avviare l'incenerimento.
    Domanda di Analisi: Come trasferiamo questa conoscenza?
    • Ipotesi A (Polling): Il WIS chiede periodicamente lo stato al MonitoringDevice.
      Pro: Il WIS controlla quando ricevere dati.
      Contro: Inefficiente (busy waiting) e introduce ritardo nella reazione (latenza di polling).
    • Ipotesi B (Dispatch Point-to-Point): Il MonitoringDevice conosce il WIS e invia un comando diretto quando lo stato cambia.
      Pro: Reattivo.
      Contro: Accoppiamento forte. Il MonitoringDevice deve sapere chi è il controllore.
    • Ipotesi C (Evento - Observer): Il MonitoringDevice emette un segnale (Evento) di "cambio stato" senza conoscere i destinatari.
      Pro: Massimo disaccoppiamento. Il sensore fa solo il sensore. Altri attori (es. Logger, GUI) possono ascoltare senza modifiche al codice.
      Contro: Traffico broadcast.
    Direzione: l'approccio a Eventi per favorire l'estensibilità e disaccoppiare la logica di rilevamento da quella di controllo è considerato più calzante alle esigenze del sistema; data la contenuta presenza di entità nel sistema del MonitoringDevice, il lato negativo dell'utilizzo di quest'ultimi è trascurabile.
    Perché l'Evento? L'evento è un messaggio "uno a molti". Ora ascolta solo il WIS, in un altro momento potrebbero aggiungersi altre entità che necessitano di questa informazione (es. interfaccia grafica). Usando gli Eventi, è possibile aggiungere queste nuove entità senza modificare il MonitoringDevice (massimo disaccoppiamento). 
    Event stateSonar : stateSonar(FULL)   // FULL = True | False (Pieno/Non Pieno)
Event sonardata : distance(DISTANCE)  // Dato grezzo

    P2.5 - Controllo del LED (Warning Device): Centralizzazione vs Distribuzione

    Il LED deve lampeggiare se l'AshStorage è pieno e l'inceneritore sta lavorando.
    Problema: Chi deve prendere la decisione di accendere il LED?
    • Opzione Distribuita: Il WarningDevice ascolta gli eventi del Sonar e dell'Inceneritore e decide autonomamente.
      Criticità: Duplicazione della logica di business nel device periferico. Difficile da mantenere.
    • Opzione Centralizzata (Scelta): L'informazione deve passare per il WIS. Il WIS è l'unico proprietario dello stato del sistema ("Core Business"). È il WIS a decidere che siamo in uno stato di "Allarme" e a ordinare al LED di accendersi.
    Tipo di Messaggio: Poiché è un ordine specifico ad un certo attuatore, useremo un Dispatch diverso per comando.
    Dispatch ledOn : ledOn(X)
Dispatch ledOff : ledOff(X)
Dispatch ledBlink : ledBlink(X)

    Perchè Dispatch? Il LED è un attuatore passivo privo di logica di business. È il WIS a decidere univocamente quando attivarlo. L'uso di Dispatch esprime semanticamente un ordine diretto e imperativo destinato a un componente specifico, garantendo che la responsabilità del controllo rimanga centralizzata nel WIS.

    P2.6 - Comunicazione Scale -> WIS

    Applicando gli stessi ragionamenti fatti per il sistema del MonitoringDevice in P2.4, la Scale emetterà un Evento ad ogni misurazione effettuata. 
    Event stateScale : stateScale(X)

    P2.8 - Calcolo del Numero di Roll Packets (RP)

    Il calcolo del numero di RP presenti nel WasteStorage spetta interamente all'Attore WIS, poiché è il responsabile di mantenere e coordinare lo stato del Core Business.
    • Il WIS, dopo aver ricevuto il PesoTotale​ aggiornato dalla Scale (P2.7), calcola il numero stimato di RP utilizzando il peso unitario di ciascun pacchetto, come definito nei requisiti:
      NumeroRP​ = PesoTotale​​ / PesoUnitario
    • Valore Standard: Si adotta il valore di 50 Kg(approssimativo) per il peso di un singolo RP, come fornito dalla richiesta del committente.

    Progettazione

    Filtraggio e Stabilizzazione delle Misurazioni del Sonar

    I sensori fisici, come il Sonar che misura la distanza delle ceneri, generano dati intrinsecamente "rumorosi" (con piccole fluttuazioni dovute a vibrazioni o fattori ambientali) e molto frequenti. Inviare ogni singola misurazione al WIS intaserebbe la comunicazione e provocherebbe decisioni instabili (ad esempio, uno stato Pieno che oscilla continuamente). Per risolvere questo problema, la responsabilità di gestione dei dati grezzi, finora del solo ed unico Sonar, viene divisa tra due attori:
    • sonardevice: Legge la misurazione (distanza) grezza e la invia al DataCleaner.
    • datacleaner: Agisce come filtro. La sua unica responsabilità è di ricevere le misurazioni e trasformare i dati instabili in informazione logica stabile. Il DataCleaner deve ignorare le piccole variazioni e applicare una sorta di stabilizzazione (ad esempio, richiedere che una condizione di soglia si mantenga per un certo periodo di tempo o numero di letture.

    Architettura Logica Monitoring Device

    La pipeline di gestione dati è così strutturata:

    1. sonardevice (Adapter): Avvia il processo sonar24.py e legge lo standard output. Trasforma le stringhe in eventi locali.
    2. datacleaner (Filter): Attore QAK sottoscritto al sonar_device. Implementa un timer: emette l'evento globale stateSonar(FULL) solo se la distanza rimane sotto DLIMT per un tempo T.
    Per dividere i compiti di ciascun attore e rendere ognuno responsabile di un compito generico, onde evitare overhead si è ritenuto necessario introdurre un nuovo attore, monitoringdevice, responsabile della facciata del sistema del MonitoringDevice: è un attore QAK principalmente responsabile di comunicare al WIS lo stato logico dell'AshStorage. Il DataCleaner dovrà quindi notificare il monitoringdevice (che poi a sua volta notificherà il WIS) solo ed esclusivamente quando viene rilevato un cambio di stato logico stabile (ad esempio, la transizione definitiva da uno stato Non Pieno a Pieno). L'introduzione dell'attore monitoringdevice è opzionale in questa fase se datacleaner emette direttamente l'evento, ma rimane utile per espansioni future.

    Architettura Warning Device

    L'appena introdotto warning_device è un attore molto semplice, in cui il suo stato cambia in base al comando imposto dal WIS:
    • ledOff: il warningdevice si sposta nello stato "off".
    • ledOn: il warningdevice si sposta nello stato "on".
    • ledBlink: il warningdevice si sposta nello stato "blink".
    QActor warningdevice context ctxmd{  
	[#
	State off initial{  
		// script turn off
	}
	Transition t0 	whenMsg ledOn -> on
			whenMsg ledOff -> off
		        whenMsg ledBlink -> blink
					
	State on{  
		// script turn on
	}
	Transition t0 	whenMsg ledOn -> on
	                whenMsg ledOff -> off
		        whenMsg ledBlink -> blink

	State blink{  
		// script turn blink
	}
	Transition t0 	whenMsg ledOn -> on
			whenMsg ledOff -> off
			whenMsg ledBlink -> blink
}

    Test Plan

    Il test plan mantiene la suite illustrata nello Sprint1, con l'aggiunta di nuovi test specifici per le funzionalità del MonitoringDevice e del WarningDevice introdotte in questo sprint:
    • Il test TestMonitoringDeviceLogicTCPOnly verifica il flusso di lavoro del sensore cenere nel sistema Qak.
      Il test invia un segnale per inizializzare la soglia di pienezza e avviare il monitoraggio.
      Simula poi sonardata con distanza < DLIMT per testare lo stato PIENO, aspettandosi l'emissione di stateSonar(true).
      Successivamente, simula sonardata con distanza > DLIMT per testare lo stato VUOTO, aspettandosi l'emissione di stateSonar(false).
    • testLEDCommandsDispatch verifica l'interfaccia e la funzionalità dell'attore warningdevice assicurando che risponda ai comandi di controllo del WIS.
      Il test inietta direttamente i comandi di Dispatch (ledOn, ledOff, ledBlink) nel contesto del WarningDevice.
      Il successo del test è determinato dalla corretta esecuzione della sequenza di forward e dall'osservazione (implicita, tramite log) che l'attore transisca e stampi il messaggio di stato corretto per ciascun comando.
